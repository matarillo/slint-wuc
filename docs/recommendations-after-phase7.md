# Phase 7 の後のおすすめ

2026-11-18 時点の整理です。
目的は、このフォークがモダンな Windows アプリの基盤として有効だと示すことです。
材料は、`docs/plan.md` の「Phase 7 の後に持ち越したこと」と、文脈を持たない Opus のサブエージェントによる読み取り専用のレビュー (同日) です。
レビューの主張のうち、推奨の上位を支える次の 4 点はコードで確かめました。

- ホストが HWND を外に出さないこと
- README がないこと
- `slint!` マクロがないこと
- カーソル画像が未対応なこと

それ以外の主張で、ビルドや GUI の実行が要るものは推測のままです。
本文では、確かめたものに【確認】、確かめていないものに【推測】と付けます。

## 結論

評価する人の印象を大きく左右するのは、持ち越しリストの中の機能よりも、使い始めて最初の 10 分で引っかかる所です。
まず、上流と同じ API の範囲で済む安い入口 (HWND の取得、導入手順) を整えます。
その上で、Windows 11 らしさが目に見える Mica と、採用を見送る理由になりうるマルチモニター DPI に進みます。

## 推奨する順序

1. `Window::window_handle()` を使えるようにする (リスト外、S)
2. 使い始めの入口を作る (リスト外、S の作業が複数)
3. Mica を、1 を使うサンプルで見せる (S〜M)
4. 上流の `examples/custom-titlebar` とライブリサイズの見た目を確かめる (リスト外、S)
5. マルチモニター DPI を検証する (S〜M、機材しだいで並行して可)
6. OLE ドラッグ&ドロップの受け側を作る (M)
7. キー入力を受けるポップアップのフォーカスを UI Automation に伝える (S〜M)

1〜7 をまとめて見せる受け皿として、ショーケース用のプローブを 1 本作ります。
Mica、ダークモードへの追従、アクセント色、ネイティブメニュー、トレイ、IME を 1 つの画面に集めます。
スクリーンショットは `tools/ui-check` で自動で撮り、上流との起動時間とメモリーの比較表を添えます。

## 各項目

### 1. `Window::window_handle()` (raw-window-handle 0.6)

- 現状【確認】:
  - core の `window_handle_06` は既定で `NotSupported` を返し、`Win32WindowAdapter` は実装していません。
  - facade (`crates/slint/Cargo.toml`) には、上流にある `raw-window-handle-06` の feature がありません。core 側の feature はあります。
- 効果: 上流と同じ API なので、フォーク独自の API は要りません。次のことがアプリ側ですぐにできるようになります。
  - 親ウィンドウを指定したファイルダイアログ (rfd など)
  - `DwmSetWindowAttribute` による Mica、角、枠の色の設定
  - 他のライブラリとの連携
- 作業: host.rs で `window_handle_06_rc` と `display_handle_06_rc` を実装し、`Win32WindowHandle` に HWND と hinstance を入れます。あわせて facade に feature を足します。
- 制約: HWND は `show()` で作られるので、それより前は取れません。上流の winit も同じです。
- 検証: 取れた HWND が一致するかを見るユニットテストを 1 本足します。

### 2. 使い始めの入口

- 現状【確認】:
  - ルートに README がありません。facade は `publish = false` です。
  - `crates/slint/lib.rs` には「`slint!` マクロはない」とあり、`docs/design/symbol-inventory.md` の「kept」という記載と食い違っています。
- 上流の feature 名 (`backend-winit`、`renderer-skia` など) を指定したアプリは、patch してもビルドに失敗するはずです【推測】。
- 作業:
  - README に `[patch.crates-io]` の手順を書きます。
  - 上流の feature 名を、何もしない feature として受け付けます。
  - `slint!` マクロを用意します。crates.io の `slint-macros` 1.19.0 の再輸出で済むかもしれません【推測】。
- 検証: 上流の examples を 2〜3 本、無改造のまま patch でビルドするスクリプトを用意します。

### 3. Mica

- 方式は確認済みです (Phase 5)。上流に API はありません。
- API: `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE, DWMSBT_MAINWINDOW など)`。公開 API として使えるのはビルド 22621 以降です。
- 前提: ウィンドウの `background: transparent`。Fluent スタイルの背景は不透明なので、アプリ側で透明にする必要があります。
- リスク【推測】: ネイティブメニューバーがあると GDI の面が残り、Mica が透けないかもしれません。
- 進め方: まず 1 の HWND を使うサンプルで見せます。フォーク独自の API (facade だけの拡張など) を足すかは、そのあとに決めます。
- 検証: ウィンドウのキャプチャで色を見ます。非アクティブ時の色になる点に注意が要ります。

### 4. タイトルバーのない窓とライブリサイズ

- `no-frame` でも、影とリサイズのために `WS_THICKFRAME` を残しています【確認】。
  - そのため DWM が角を丸めて枠線を描き、アプリが自分で描く角と二重に見える可能性があります【推測】。
  - ポップアップでは丸めと枠線を外してあるので、透明背景の `no-frame` に同じ処理を当てるのは S です。
  - ただし winit とは挙動が変わります。
- `WindowMoveArea` は移動を始めるだけです【確認】。ダブルクリックでの最大化とスナップレイアウトの表示は出ません。上流にも API はありません。
- ライブリサイズ: スパイク S1 で、内容が枠より 1〜2 フレーム遅れることがわかっています。ただ、目視での確認の記録がありません。
  - 評価する人が最初に試す操作なので、見た目を確かめます。
  - 必要なら、サイズ変更中だけ `WM_SIZE` の中で同期します (S〜M)。
- 検証: 上流の `examples/custom-titlebar` をプローブにして、`ui-check` で撮ります。

### 5. マルチモニター DPI

- コードとユニットテストはあります【確認】。
  - `WM_GETDPISCALEDSIZE` と `WM_DPICHANGED` の処理
  - ユニットテスト `dpi_changes_keep_the_logical_size`
- 確かめていないこと:
  - モニターをまたぐときのシェルの振る舞い
  - ポップアップの移動先
  - IME の候補ウィンドウの位置
- 検証: 実機がなければ、仮想ディスプレイドライバー (IddCx) で、倍率の違うモニターを 1 台足します (管理者権限が要ります)。`SetWindowPos` で 2 台目へ動かし、`SLINT_FORK_TRACE_DPI` とスナップショットで確かめれば、ほぼ自動化できます。

### 6. OLE ドラッグ&ドロップの受け側

- エクスプローラーからのファイルドロップを受けます。送り側 (`start_drag`) は後にします。
- 経路: core の `WindowInner::process_drag_event` を使います。上流では Qt バックエンドが使っているもので、`.slint` 側は既存の `DropArea` のままです。
- 作業:
  - `host/drop.rs` に `IDropTarget` を実装し、`CF_HDROP` と `CF_UNICODETEXT` を変換します。
  - ウィンドウの作成時に `RegisterDragDrop` を呼びます。
- リスク:
  - `RoInitialize` の後に `OleInitialize` を呼べるか
  - ドロップの効果の対応
  - 昇格したプロセスでの制限
- 検証: 偽の `IDataObject` で `DragEnter`、`DragOver`、`Drop` を直接呼ぶテストにすれば、マウスを使わずに済みます。

### 7. ポップアップのフォーカスを UI Automation に伝える

- キー入力を受けるポップアップが変わったら、そのポップアップの側にフォーカスを、元のウィンドウに非フォーカスを AccessKit で伝えます。
- リスク【推測】: アクティブにならないウィンドウから出したフォーカスを、ナレーターが受け入れるかはわかりません。
- 検証: `tests/input` の UI Automation クライアントのテストで自動化できます。

### ショーケースのプローブと性能比較

- `probe-perf` はフォークの内部を使うので、上流は測れません。
- `tools/upstream-gallery` を外から起動し、最初のフレームまでの時間とメモリーを測れば、上流と比べられます (S)。
- 起動から最初の同期まで約 40 ms、アイドル時の CPU 0 は強い材料ですが、比べる相手がないと伝わりません。

## フォーク独自の拡張の考え方

判断事項の 1 を決めるための材料です。
「`slint::windows` のような拡張」とは、上流が winit バックエンド向けに用意している拡張と同じ形で、このフォーク専用の Windows 向け拡張を Rust の facade に足すことです。

### 上流の前例

上流の `slint` クレートには、特定のバックエンド向けの拡張がいくつかあります【確認】。

- `slint::winit_030` モジュール (feature は `unstable-winit-030`)
  - `slint::Window` に、拡張トレイト `WinitWindowAccessor` が付きます。
    - `with_winit_window`: 中の winit のウィンドウを触れます。
    - `on_winit_window_event`: ウィンドウのイベントを横取りできます。
  - `BackendSelector` にも、ウィンドウを作るときの属性に手を入れる `with_winit_window_attributes_hook` などがあります。
  - ドキュメントには次の注意があります。
    - マイナーリリースで変わりうる。
    - Slint 自身が管理する状態 (カーソル、サイズ、IME など) は上書きされうる。
- `slint::android` と `unstable-wgpu-*` も同じ考え方です。上流の公開 API でカバーしない部分を、名前に `unstable-` が付いた feature で個別に出しています。

上流で Mica を使うときも、この拡張を通します。
winit 0.30 の Windows 向け拡張に `set_system_backdrop(BackdropType::MainWindow)` があります【確認】。

```rust
use slint::winit_030::{WinitWindowAccessor, winit::platform::windows::{WindowExtWindows, BackdropType}};
app.window().with_winit_window(|w| w.set_system_backdrop(BackdropType::MainWindow));
```

### フォークでの具体像 (案)

```rust
// Cargo.toml: slint = { ..., features = ["unstable-windows"] }
use slint::windows::{WindowsWindowExt, Backdrop};

app.window().set_system_backdrop(Backdrop::Mica);        // DWM の背景素材
app.window().set_corner_preference(Corners::Round);      // 角、枠の色、タイトルバーの色
app.window().on_window_message(|msg, wparam, lparam| …); // on_winit_window_event に当たるもの
app.window().with_composition_root(|visual| …);          // 独自の Visual や D3D の面を差し込む
```

- 形は上流に合わせます。
  - `unstable-` 付きの feature にします。
  - `Window` への拡張トレイトにします。
  - 「変わりうる」「Slint が管理する状態は上書きされうる」と明記します。
- 中身はフォーク独自です。`winit_030` をまねることはできません。フォークには winit がないので、winit の型を返せないからです。

### 上流との整合性

| 観点 | 合うか |
|---|---|
| 拡張の出し方 (unstable feature、拡張トレイト、注意書き) | 合わせられる |
| アプリのコード | 合わない。上流向けの `winit_030` のコードはフォークでビルドできず、フォーク向けの拡張のコードは上流でビルドできない。両方で動かすには `cfg` で分ける必要がある |
| `.slint` 側 | 拡張できない。コンパイラーは上流のものを改造せずに使うので、`Window` に `backdrop: mica` のようなプロパティは足せない。拡張は Rust のコードからだけになる |
| 将来の C++ や Node | 拡張ごとに、言語ごとの窓口が要る (上流の `winit_030` も Rust だけ) |

raw window handle (推奨 1) は上流の公開 API そのものです。
アプリが HWND を取って `DwmSetWindowAttribute` を自分で呼ぶコードは、上流の winit でも、このフォークでも、同じまま動きます。

### 判断の目安

- raw window handle だけにする場合
  - 上流とのコードの互換が最も高く、コストも最小です。
  - Mica、角、枠の色は、アプリが DWM を呼べば足ります。
  - Mica がちゃんと透けるには、ホスト側の協力が要るかもしれません (ネイティブメニューバーの GDI 面など)【推測】。その場合も、要るのはホストの修正だけです。
- `unstable-windows` の拡張を足す場合、HWND だけではできないことに意味があります。
  - メッセージの横取り: アプリが自前でウィンドウをサブクラス化すると、ホストの処理とぶつかります。
  - Composition のビジュアルツリーへの差し込み: WinUI 系の Visual、動画、D3D のスワップチェーンを、Slint の画面に混ぜられます。上流のどのバックエンドにもできないことで、このフォークならではの強みになります。

おすすめは、まず raw window handle で Mica を見せることです。
拡張は、Composition への差し込みのように HWND では足りない用途が出たときに足します。

## 最低 OS の考え方

判断事項の 4 を決めるための材料です。

### 最低 OS が決めること

最低 OS は、「このフォークで作ったアプリは、このビルド以降の Windows で動く」という約束です。
次の 3 つが、これで決まります。

- アプリを動かせる利用者の範囲。最低 OS より古い Windows は対象外になります。
- コードの書き方。最低 OS より新しい OS でしか使えない機能を呼ぶ箇所には、OS を判定する処理と、使えないときの代わりの動作が要ります。
- 確かめる範囲。約束した OS では、実際に動くことを確かめる必要があります。

### 現状

- `docs/plan.md` の前提は、Windows 11 のみ、ビルド 22000 以降です。22H2 (22621) 以降の機能は、実行時に判定することになっています。
- コードには、OS のバージョンを判定する処理がまだありません【確認】。今は、22000 より新しい OS を要する機能を使っていないためです。
- 動作を確かめたのは、開発機の Windows 11 25H2 (ビルド 26200) だけです。22000 と 22621 では確かめていません。

### 開発環境の SDK とは関係なく決められる

- 最低 OS は、開発機に入っている Windows SDK のバージョンには左右されません。開発機の SDK は 10.0.28000.0 です。
- `windows` クレートは、Win32 と WinRT の API の定義を自分で持っています。どの API が使えるかは、SDK ではなく、アプリを実行する OS で決まります。
- SDK を使うのは、リンクと、`tools/cpp-headers` のテストで `cl.exe` がヘッダーを読むときだけです。
- 新しい SDK でビルドしたアプリでも、古い OS で動かせます。新しい機能を呼ぶ前に OS を判定すればよく、これが「実行時の判定」です。

### 2 つの方針

Mica を例にします。
Mica を出す公開 API (`DWMWA_SYSTEMBACKDROP_TYPE`) が効くのは 22621 以降です。

| | 最低 OS を 22621 に上げる | 22000 のまま、実行時に判定する |
|---|---|---|
| 22000 の利用者 | 対象外。起動時に、非対応の OS だと知らせて止めることもできる | 動く。ただし Mica は出ない |
| Mica を使うコード | 判定せずに呼べる | OS を判定し、使えないときの代わりの見た目に切り替える分岐が要る |
| 代わりの見た目 | 要らない | 要る。Mica を前提に背景を透明にしたアプリは、22000 で背景が抜けて見える可能性がある【推測】。不透明な背景に切り替えるなどの決まりが要る |
| 文書 | 「22621 以降」と書くだけ | 「22000 以降。ただし、この機能は 22621 以降」と機能ごとに書く |
| 確かめる範囲 | 22621 以降 | 22621 以降に加えて、22000 での代わりの動作 |

対象を絞れば、コードも文書も単純になります。
対象を広く取ると、新しい OS 向けの機能を足すたびに、判定と代わりの動作を用意することになります。
どちらを選んでも、Mica は新しい OS 向けの機能として最初のものになるので、そこでの扱いが以後の機能の前例になります。

### 判断に使える事実

- サポート期限 (Microsoft のライフサイクルの規則からの推定で、確かめていない): 2026-11 時点で、22000 (21H2)、22621 (22H2)、22631 (23H2) は、どのエディションもサポートが終わっているはずです。サポートが続いているのは、24H2 (26100) の Enterprise、Education、LTSC と、25H2 (26200) です。
- 22000 には、文書化されていない `DWMWA_MICA_EFFECT` があります。公開 API だけで Mica を扱うなら、22621 以降が条件になります。
- 古いビルドで確かめるには、仮想マシンなどの環境が別に要ります。今の開発環境で確かめられるのは 26200 だけです。

## オーナーの判断が必要なこと

1. フォーク独自の API をどこまで認めるか。facade だけに `slint::windows` のような拡張を足すか、HWND とサンプルにとどめるか。Mica、タイトルバー、ハイコントラストのすべてに関わる。考え方は「フォーク独自の拡張の考え方」を参照。
2. 見せる相手は Rust の開発者だけか、C++ の開発者も含むか。
3. 配布の形 (git の依存、別名での crates.io 公開、patch の手順だけ) とライセンスの表記。README の内容が決まる。
4. 最低 OS をビルド 22000 のままにするか、上げるか。Mica の公開 API は 22621 以降。考え方は「最低 OS の考え方」を参照。
5. マルチモニターの検証に、仮想ディスプレイドライバーを入れてよいか (管理者権限が要る)。
6. 透明背景の `no-frame` ウィンドウで、DWM の枠線と角丸を外すか。挙動が winit と変わる。
7. slokk-slint をそのままショーケースにするか、デモ用のプローブを別に作るか。

1、3、4 は推奨 1〜3 の作業の形を決めるので、先に決めると進めやすいです。

- `no-frame` の窓で DWM の枠が二重に見えるか
- ライブリサイズ時の見た目
- Mica とネイティブメニューバーの組み合わせ
