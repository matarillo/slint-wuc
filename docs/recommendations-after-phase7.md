# Phase 7 の後のおすすめ

2026-11-18 時点の整理です。
目的は、このフォークがモダンな Windows アプリの基盤として有効だと示すことです。
材料は、`docs/plan.md` の「Phase 7 の後に持ち越したこと」と、文脈を持たない Opus のサブエージェントによる読み取り専用のレビュー (同日) です。
レビューの主張のうち、推奨の上位を支える次の 4 点はコードで確かめました。

- ホストが HWND を外に出さないこと (2026-11-19 に `Window::window_handle()` で出すようにした)
- README がないこと (2026-11-19 に書いた)
- `slint!` マクロがないこと (2026-11-19 に足した)
- カーソル画像が未対応なこと

それ以外の主張で、ビルドや GUI の実行が要るものは推測のままです。
本文では、確かめたものに【確認】、確かめていないものに【推測】と付けます。

## 結論

評価する人の印象を大きく左右するのは、持ち越しリストの中の機能よりも、使い始めて最初の 10 分で引っかかる所です。
まず、上流と同じ API の範囲で済む安い入口 (HWND の取得、導入手順) を整えます。
その上で、Windows 11 らしさが目に見える Mica と、採用を見送る理由になりうるマルチモニター DPI に進みます。

## 推奨する順序

1. `Window::window_handle()` を使えるようにする (リスト外、S)。2026-11-19 に済み
2. 使い始めの入口を作る (リスト外、S の作業が複数)。2026-11-19 に済み
3. Mica を、1 を使うサンプルで見せる (S〜M)
4. 上流の `examples/custom-titlebar` とライブリサイズの見た目を確かめる (リスト外、S)。2026-11-19 に済み (透けない角を直した)
5. マルチモニター DPI を検証する (S〜M、機材しだいで並行して可)
6. OLE ドラッグ&ドロップの受け側を作る (M)
7. キー入力を受けるポップアップのフォーカスを UI Automation に伝える (S〜M)

1〜7 をまとめて見せる受け皿として、ショーケース用のプローブを 1 本作ります。
Mica、ダークモードへの追従、アクセント色、ネイティブメニュー、トレイ、IME を 1 つの画面に集めます。
スクリーンショットは `tools/ui-check` で自動で撮り、上流との起動時間とメモリーの比較表を添えます。

## 各項目

### 1. `Window::window_handle()` (raw-window-handle 0.6)

2026-11-19 に済みました。

- 元の状態:
  - core の `window_handle_06` は既定で `NotSupported` を返し、`Win32WindowAdapter` は実装していませんでした。
  - facade (`crates/slint/Cargo.toml`) には、上流にある `raw-window-handle-06` の feature がありませんでした。core 側の feature はありました。
- 効果: 上流と同じ API なので、フォーク独自の API は要りません。次のことがアプリ側ですぐにできるようになります。
  - 親ウィンドウを指定したファイルダイアログ (rfd など)
  - `DwmSetWindowAttribute` による Mica、角、枠の色の設定
  - 他のライブラリとの連携
- したこと:
  - host.rs で `window_handle_06_rc` と `display_handle_06_rc` を実装しました。`Win32WindowHandle` には HWND と hinstance (`GWLP_HINSTANCE`) を、表示側には `WindowsDisplayHandle` を入れます。
  - facade に、上流と同じ名前の feature `raw-window-handle-06` を足しました。
  - 返すハンドルは、取り出すたびに窓に HWND を尋ねます。`show()` の前に取ったハンドルでも、`show()` の後には HWND が取れます。
  - ハンドルは窓を強参照で持ちます。上流の winit が winit の窓を `Arc` で持つのと同じで、持っている間は HWND が壊れません。
- 制約: HWND は `show()` で作られるので、それより前は `HandleError::Unavailable` になります。上流の winit も、窓ができる前は同じエラーです。アプリは `show()` の後に取ります (`run()` の前に `show()` を呼ぶ)。
- 検証:
  - ユニットテスト `host::tests::the_window_handle_is_the_hwnd` で、HWND を作る前は `Unavailable`、作った後は HWND と hinstance が一致することを確かめます。HWND は表示しないので、デスクトップに窓は出ません。
  - `probe-mica` は、`create_hwnd_for_testing` の代わりに `window_handle()` で HWND を取るようにしました。上流のアプリと同じ書き方で、core の内部には触れません。`tools/backdrop-capture.ps1` で、変更の前後の色が同じであることを確かめました (MenuBar なしで Mica あり: 中央 `#F3F3F3`、Mica なし: 中央 `#FF00FF`、ネイティブの MenuBar: 中央 `#FFFFFF`)。

  - README の末尾に、フォークを開発する人向けの節を置きました。`reference/slint-1.19.0` の用意の仕方 (上流のタグ `v1.19.0` の clone。タグは実在を確認) と、それがないと失敗するものを書いています。アプリを作る人には `reference/` は要りません。

- 検証【確認】:
  - `crates/slint/tests/macro.rs`: `slint!` で作ったコンポーネント (`Button`、プロパティ、コールバック) が動くこと。
  - `tools/upstream-examples.ps1`: 上流の `memory` (`slint!`、`default-features = false`)、`slide_puzzle` (`build.rs`)、`system-tray` (`slint!`、既定の feature) を、ソースは無改造のまま、git の依存と patch の両方でビルドします。6 通りすべて通り、`Cargo.lock` の `slint` がフォーク版であることも確かめます。例は上流のリポジトリと同じ深さに置きます。`../../logo` の画像を読むものがあるためです。
  - patch の形は `slint = "1.19"` で書いています。crates.io の最新がまだ 1.19.0 なので、1.20 が出たあとも patch が選ばれるかは確かめられていません【推測】。
  - `reference/` を一時的に外して確かめたこと: `cargo build -p slint` は通ります。ワークスペースのビルドは、`tests/probe`、`tests/driver`、`tests/screenshots` のビルドスクリプトで失敗します。

### 3. Mica

- 方式は確認済みです (Phase 5)。上流に API はありません。
- API: `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE, DWMSBT_MAINWINDOW など)`。公開 API として使えるのはビルド 22621 以降です。
- 前提: ウィンドウの `background: transparent`。Fluent スタイルの背景は不透明なので、アプリ側で透明にする必要があります。
- 2026-11-19 に確かめたこと【確認】 (`probe-mica`、背景が透明な普通の枠の窓):

  | 窓 | Mica を設定したとき |
  |---|---|
  | MenuBar なし | 窓全体が Mica |
  | ネイティブの MenuBar | タイトルバーだけ Mica。メニューバーとクライアント領域は白 |
  | Slint 描画の MenuBar (`SLINT_NO_MUDA=1`) | メニューバーも含めて窓全体が Mica |

  - ネイティブのメニューバーは GDI のリダイレクション面に描かれ、その面が白い下地になるためです (`docs/design/windows.md` の Menus)。
  - 同じ日に、リダイレクション面を付けるのを、作る時点で MenuBar がある窓だけにしました。それまでは、トップレベルの窓すべてに付けていたので、MenuBar がなくても透けませんでした。
  - 面を残したまま透明にする実験 (winit と同じ `DwmEnableBlurBehindWindow`、黒の背景ブラシ) は、どちらも効きませんでした。上流の winit も、メニューバーのある窓では透明をやめています。
- 決めたこと (2026-11-19):
  - Mica はできるかぎり効かせます。メニューバーをネイティブにすることは要件ではありません。
  - 既定は、ネイティブのメニューバーのままにします。F10 と Alt+文字でのメニュー操作と、メニューの UI Automation への公開を残すためです。
  - MenuBar と Mica を同じ窓で使いたいアプリは、短期的には Slint 描画のメニューバーを選びます。その代わり、Alt/F10 の入口とメニューバーの項目の役割 (UI Automation) が欠けます。この 2 つは、上流が生成するウィジェットのコードの中にあるので、フォークでは直せません。
  - 「Mica と、全機能のメニューバーの併用」は積み残しです (`docs/plan.md`)。方式の候補は、ホストがコンポジションでメニューバーを描き、ドロップダウンを `TrackPopupMenuEx` で出すことです (L)。
  - Slint 描画への切り替え方は、まだ決めていません。今は環境変数 `SLINT_NO_MUDA` です。上流にも同じ名前があるので、上流でも同じ挙動になります。ただし、プロセス全体に効き、ネイティブのコンテキストメニューも止まります。窓ごとに選ばせるなら、フォーク独自の API になります (判断事項 1)。Mica を見せるサンプルを作るときに決めます。
- 進め方: まず 1 の HWND を使うサンプルで見せます。`probe-mica` は 2026-11-19 から `window_handle()` で HWND を取っており、その形になっています。フォーク独自の API (facade だけの拡張など) を足すかは、そのあとに決めます。
- 検証: プローブを、画面の右端に置いた単色の下地の窓の上に重ね、その矩形だけをキャプチャして色を見ます (`tools/backdrop-capture.ps1`)。Mica は、アクティブな窓では壁紙の色味が乗ります。

### 4. タイトルバーのない窓とライブリサイズ

- `no-frame` でも、影とリサイズのために `WS_THICKFRAME` を残しています【確認】。
  - 上流の winit も `WS_THICKFRAME` を残し、角の丸めを OS に任せています【確認】。違いは、上流が `WS_CAPTION`、フォークが `WS_POPUP` であることだけです。
  - 上流の `examples/custom-titlebar` (`probe-titlebar` と `upstream-titlebar`) で比べると、DWM の枠線と角丸の見え方は同じでした (2026-11-19、オーナーの目視)。外す必要はありません。
  - 角の外側は、上流では透けて、フォークでは白くなっていました。リダイレクション面が原因で、MenuBar のない窓には面を付けないようにして直しました。今は四隅とも上流と同じに透けます (キャプチャで確認)。
  - `WS_CAPTION` がないことで、Win+矢印でのスナップや最小化のアニメーションが変わるかは、確かめていません。
- `WindowMoveArea` は移動を始めるだけです【確認】。ダブルクリックでの最大化とスナップレイアウトの表示は出ません。上流にも API はありません。
- ライブリサイズ: スパイク S1 で、内容が枠より 1〜2 フレーム遅れることがわかっています。
  - `probe-titlebar` で、リダイレクション面がある場合とない場合の両方を、オーナーが試しました。違和感はありませんでした (2026-11-19)。
  - 同期の作業 (サイズ変更中だけ `WM_SIZE` の中で同期する、S〜M) は、今は要りません。

### 6. OLE ドラッグ&ドロップの受け側

- エクスプローラーからのファイルドロップを受けます。送り側 (`start_drag`) は後にします。
- 経路: core の `WindowInner::process_drag_event` を使います。上流では Qt バックエンドが使っているもので、`.slint` 側は既存の `DropArea` のままです。
- 作業:
  - `host/drop.rs` に `IDropTarget` を実装し、`CF_HDROP` と `CF_UNICODETEXT` を変換します。
  - ウィンドウの作成時に `RegisterDragDrop` を呼びます。
- リスク:
  - `RoInitialize` の後に `OleInitialize` を呼べるか
  - ドロップの効果の対応
  - 昇格したプロセスでの制限
- 検証: 偽の `IDataObject` で `DragEnter`、`DragOver`、`Drop` を直接呼ぶテストにすれば、マウスを使わずに済みます。

## フォーク独自の拡張の考え方

判断事項の 1 を決めるための材料です。
「`slint::windows` のような拡張」とは、上流が winit バックエンド向けに用意している拡張と同じ形で、このフォーク専用の Windows 向け拡張を Rust の facade に足すことです。

### 上流の前例

上流の `slint` クレートには、特定のバックエンド向けの拡張がいくつかあります【確認】。

- `slint::winit_030` モジュール (feature は `unstable-winit-030`)
  - `slint::Window` に、拡張トレイト `WinitWindowAccessor` が付きます。
    - `with_winit_window`: 中の winit のウィンドウを触れます。
    - `on_winit_window_event`: ウィンドウのイベントを横取りできます。
  - `BackendSelector` にも、ウィンドウを作るときの属性に手を入れる `with_winit_window_attributes_hook` などがあります。
  - ドキュメントには次の注意があります。
    - マイナーリリースで変わりうる。
    - Slint 自身が管理する状態 (カーソル、サイズ、IME など) は上書きされうる。
- `slint::android` と `unstable-wgpu-*` も同じ考え方です。上流の公開 API でカバーしない部分を、名前に `unstable-` が付いた feature で個別に出しています。

上流で Mica を使うときも、この拡張を通します。
winit 0.30 の Windows 向け拡張に `set_system_backdrop(BackdropType::MainWindow)` があります【確認】。

```rust
use slint::winit_030::{WinitWindowAccessor, winit::platform::windows::{WindowExtWindows, BackdropType}};
app.window().with_winit_window(|w| w.set_system_backdrop(BackdropType::MainWindow));
```

### フォークでの具体像 (案)

```rust
// Cargo.toml: slint = { ..., features = ["unstable-windows"] }
use slint::windows::{WindowsWindowExt, Backdrop};

app.window().set_system_backdrop(Backdrop::Mica);        // DWM の背景素材
app.window().set_corner_preference(Corners::Round);      // 角、枠の色、タイトルバーの色
app.window().on_window_message(|msg, wparam, lparam| …); // on_winit_window_event に当たるもの
app.window().with_composition_root(|visual| …);          // 独自の Visual や D3D の面を差し込む
```

- 形は上流に合わせます。
  - `unstable-` 付きの feature にします。
  - `Window` への拡張トレイトにします。
  - 「変わりうる」「Slint が管理する状態は上書きされうる」と明記します。
- 中身はフォーク独自です。`winit_030` をまねることはできません。フォークには winit がないので、winit の型を返せないからです。

### 上流との整合性

| 観点 | 合うか |
|---|---|
| 拡張の出し方 (unstable feature、拡張トレイト、注意書き) | 合わせられる |
| アプリのコード | 合わない。上流向けの `winit_030` のコードはフォークでビルドできず、フォーク向けの拡張のコードは上流でビルドできない。両方で動かすには `cfg` で分ける必要がある |
| `.slint` 側 | 拡張できない。コンパイラーは上流のものを改造せずに使うので、`Window` に `backdrop: mica` のようなプロパティは足せない。拡張は Rust のコードからだけになる |
| 将来の C++ や Node | 拡張ごとに、言語ごとの窓口が要る (上流の `winit_030` も Rust だけ) |

raw window handle (推奨 1) は上流の公開 API そのものです。
アプリが HWND を取って `DwmSetWindowAttribute` を自分で呼ぶコードは、上流の winit でも、このフォークでも、同じまま動きます。

### 判断の目安

- raw window handle だけにする場合
  - 上流とのコードの互換が最も高く、コストも最小です。
  - Mica、角、枠の色は、アプリが DWM を呼べば足ります。
  - Mica がちゃんと透けるには、ホスト側の協力が要るかもしれません (ネイティブメニューバーの GDI 面など)【推測】。その場合も、要るのはホストの修正だけです。
- `unstable-windows` の拡張を足す場合、HWND だけではできないことに意味があります。
  - メッセージの横取り: アプリが自前でウィンドウをサブクラス化すると、ホストの処理とぶつかります。
  - Composition のビジュアルツリーへの差し込み: WinUI 系の Visual、動画、D3D のスワップチェーンを、Slint の画面に混ぜられます。上流のどのバックエンドにもできないことで、このフォークならではの強みになります。

おすすめは、まず raw window handle で Mica を見せることです。
拡張は、Composition への差し込みのように HWND では足りない用途が出たときに足します。

## 最低 OS の考え方

判断事項の 4 を決めるための材料です。

### 最低 OS が決めること

最低 OS は、「このフォークで作ったアプリは、このビルド以降の Windows で動く」という約束です。
次の 3 つが、これで決まります。

- アプリを動かせる利用者の範囲。最低 OS より古い Windows は対象外になります。
- コードの書き方。最低 OS より新しい OS でしか使えない機能を呼ぶ箇所には、OS を判定する処理と、使えないときの代わりの動作が要ります。
- 確かめる範囲。約束した OS では、実際に動くことを確かめる必要があります。

### 現状

- `docs/plan.md` の前提は、Windows 11 のみ、ビルド 22000 以降です。22H2 (22621) 以降の機能は、実行時に判定することになっています。
- コードには、OS のバージョンを判定する処理がまだありません【確認】。今は、22000 より新しい OS を要する機能を使っていないためです。
- 動作を確かめたのは、開発機の Windows 11 25H2 (ビルド 26200) だけです。22000 と 22621 では確かめていません。

### 開発環境の SDK とは関係なく決められる

- 最低 OS は、開発機に入っている Windows SDK のバージョンには左右されません。開発機の SDK は 10.0.28000.0 です。
- `windows` クレートは、Win32 と WinRT の API の定義を自分で持っています。どの API が使えるかは、SDK ではなく、アプリを実行する OS で決まります。
- SDK を使うのは、リンクと、`tools/cpp-headers` のテストで `cl.exe` がヘッダーを読むときだけです。
- 新しい SDK でビルドしたアプリでも、古い OS で動かせます。新しい機能を呼ぶ前に OS を判定すればよく、これが「実行時の判定」です。

### 2 つの方針

Mica を例にします。
Mica を出す公開 API (`DWMWA_SYSTEMBACKDROP_TYPE`) が効くのは 22621 以降です。

| | 最低 OS を 22621 に上げる | 22000 のまま、実行時に判定する |
|---|---|---|
| 22000 の利用者 | 対象外。起動時に、非対応の OS だと知らせて止めることもできる | 動く。ただし Mica は出ない |
| Mica を使うコード | 判定せずに呼べる | OS を判定し、使えないときの代わりの見た目に切り替える分岐が要る |
| 代わりの見た目 | 要らない | 要る。Mica を前提に背景を透明にしたアプリは、22000 で背景が抜けて見える可能性がある【推測】。不透明な背景に切り替えるなどの決まりが要る |
| 文書 | 「22621 以降」と書くだけ | 「22000 以降。ただし、この機能は 22621 以降」と機能ごとに書く |
| 確かめる範囲 | 22621 以降 | 22621 以降に加えて、22000 での代わりの動作 |

対象を絞れば、コードも文書も単純になります。
対象を広く取ると、新しい OS 向けの機能を足すたびに、判定と代わりの動作を用意することになります。
どちらを選んでも、Mica は新しい OS 向けの機能として最初のものになるので、そこでの扱いが以後の機能の前例になります。

### 判断に使える事実

- サポート期限 (Microsoft のライフサイクルの規則からの推定で、確かめていない): 2026-11 時点で、22000 (21H2)、22621 (22H2)、22631 (23H2) は、どのエディションもサポートが終わっているはずです。サポートが続いているのは、24H2 (26100) の Enterprise、Education、LTSC と、25H2 (26200) です。
- 22000 には、文書化されていない `DWMWA_MICA_EFFECT` があります。公開 API だけで Mica を扱うなら、22621 以降が条件になります。
- 古いビルドで確かめるには、仮想マシンなどの環境が別に要ります。今の開発環境で確かめられるのは 26200 だけです。

## 配布の形の考え方

判断事項の 3 を決めるための材料です。
3 つの形それぞれで、アプリを作る人が何をするかを書きます。
どの形でも、使えるのは Rust だけです。C++ のバインディングは移植していません (`docs/design/bindings-gap.md`)。

### どの形でも同じこと

アプリは 2 つの部品を組み合わせて使います。

- `.slint` を Rust に変換するコンパイラー: crates.io の上流の `slint-build` を、そのまま使います。フォークにコンパイラーはありません。
- 生成されたコードが呼ぶランタイム: フォークの `slint` を使います。上流の `slint` の代わりです。

そのため、アプリを作る人は次のことを守る必要があります。

- `slint-build` を `"=1.19.0"` と完全一致で指定する【確認】。
  - 生成されたコードは、`slint::VersionCheck_1_19_0` のように、コンパイラーのバージョンの名前を持つ型を参照します。フォークにあるのは `VersionCheck_1_19_0` だけです。
  - `"1.19"` と書くと、Cargo は 1.x の最新 (上流が 1.20 を出していれば 1.20) を選び、ビルドに失敗します。
- 上流だけにある API の feature を指定しない。バックエンドとレンダラーの選択に当たる feature (`backend-winit`、`renderer-skia` など) は、2026-11-19 から何もしない feature として受け付けます。`unstable-*`、`live-preview`、`system-testing` を指定すると、Cargo が「その feature はない」と止まります。
- 上流だけにある API を使わない。`slint::winit_030`、ソフトウェアレンダラー、独自のプラットフォームの設定などです。`slint!` マクロは 2026-11-19 から使えます。
- Windows 11 で、Rust 1.95 以降を使う。

アプリの依存関係には `i-slint-common` が 2 つ載ります。コンパイラー用とランタイム用に 1 つずつで、どちらも実際にビルドされます【確認】。

- crates.io 版は、`slint-build` → `i-slint-compiler` が使います。`slint-build` は `[build-dependencies]` なので、`build.rs` の実行ファイルにだけ組み込まれます。ビルドの途中で `.slint` を Rust のソースに変換したら、役目は終わります。
- フォーク版は、`slint` → `i-slint-core` が使います。アプリの実行ファイルにリンクされるのは、こちらだけです。

2 つは別々の実行ファイル (`build.rs` とアプリ本体) に入るので、衝突しません。
コンパイラーからランタイムに渡るのは、生成された Rust のソースのテキストだけで、`i-slint-common` の型が 2 つの間を行き来することはありません。
Cargo は、名前とバージョンが同じでも、取得元 (path や git と crates.io) が違えば別のクレートとして扱います。
このリポジトリの `tests/probe` も、`cargo tree` で見るとこの形になっていて、ビルドできています【確認】。

ただし、`i-slint-common` まで patch で差し替えると、コンパイラーがフォーク版でビルドされることになります。動くかどうかは確かめていません。

### 共通の前提: リポジトリの公開

git の依存と patch の手順は、どちらもフォークのリポジトリをどこかに公開する必要があります。今はリモートがありません【確認】。
公開する前でも、`path = "F:/..."` と書けば、手元で同じことを試せます。

### git の依存

アプリの `Cargo.toml`:

```toml
[dependencies]
slint = { git = "https://github.com/<owner>/<repo>", rev = "<commit>" }

[build-dependencies]
slint-build = "=1.19.0"
```

- アプリを作る人がすること: 上の 2 行を書きます。Rust のソースは上流向けのままで、`slint::include_modules!()` も同じです。
- 更新: `rev` (または `tag`) を書き換えます。`branch` を指定した場合は `cargo update -p slint` を実行します。`Cargo.lock` が commit を固定するので、実行しない限り変わりません。
- 上流に戻す: `slint = "1.19"` に書き換えます。
- 制約:
  - git の依存を持つクレートは crates.io に公開できません。アプリには問題ありませんが、ウィジェット集のようなライブラリをこのフォーク向けに作って公開することはできません。
  - 初回のビルドで、Cargo がリポジトリ全体を取得します。

### patch の手順だけ

アプリの `Cargo.toml`:

```toml
[dependencies]
slint = "1.19"            # 上流向けのまま

[build-dependencies]
slint-build = "=1.19.0"

[patch.crates-io]
slint = { git = "https://github.com/<owner>/<repo>", rev = "<commit>" }
```

- アプリを作る人がすること: `[patch.crates-io]` の 2 行を足し、`slint-build` を完全一致にします。`[dependencies]` は上流向けのままです。
- 上流に戻す: `[patch.crates-io]` を消すだけです。上流とフォークを比べたい人には、これがいちばん手軽です。
- 更新: git の依存と同じです。
- 制約:
  - patch はアプリ (ワークスペースの最上位) の `Cargo.toml` でしか効きません。ライブラリが patch を書いても、そのライブラリを使う側には伝わりません。
  - `[dependencies]` のバージョン指定が 1.19.0 を受け入れない場合 (`"1.20"` など)、Cargo は「patch を使わなかった」と警告するだけで、上流の `slint` を使います。気づかずに上流でビルドしてしまうことがあります。
  - `slint = "1.19"` のとき、crates.io に 1.20 があっても patch の 1.19.0 が選ばれるはずです【推測】。確実にするなら `"=1.19.0"` と書きます。
- git の依存との違いは、`[dependencies]` を上流向けのまま残せることだけです。中身は同じものを取得します。

### 別名で crates.io に公開

`slint` という名前は crates.io で上流が使っているので、別の名前が要ります。仮に `slint-wuc` とします。
アプリの `Cargo.toml`:

```toml
[dependencies]
slint = { package = "slint-wuc", version = "0.1" }

[build-dependencies]
slint-build = "=1.19.0"
```

- アプリを作る人がすること: 上の 2 行を書きます。`package` で名前を付け替えるので、ソースの中では `slint` のまま使えます。生成されたコードも `slint::` を参照するので、これで動きます【推測】。
- 更新: 普通の crates.io の依存と同じで、`cargo update` やバージョンの書き換えです。
- 上流に戻す: `slint = "1.19"` に書き換えます。
- 利点: git もリポジトリの公開も要りません。ライブラリもこのフォーク向けに作って crates.io に公開できます。
- フォークの側でする作業:
  - `slint`、`i-slint-core`、`i-slint-common`、`i-slint-core-macros` の 4 つすべてに別名を付けます。どれも crates.io で上流が使っている名前です。テスト用の `i-slint-backend-testing` は公開しないなら不要です。
  - `publish = false` を外し、`repository` と `authors` をフォークのものに直します。今は上流の値です【確認】。
  - バージョンはフォーク独自の番号にできます。ただし、どのコンパイラーと組むか (今は 1.19.0) を README に書く必要があります。
  - 公開したバージョンは消せません (取り下げ (yank) はできる)。名前も一度取ると残ります。

### ライセンスの表記

フォークのファイルは、上流の著作権表示と 3 つのライセンス (GPL-3.0、Royalty-free 2.0、Software 3.0) のまま残っています【確認】。
アプリを作る人は、上流と同じく、3 つのうちどれで使うかを選ぶことになります。
どの形でも、README に次のことを書く必要があります。

- 上流の Slint ではなく、その派生物であること。問い合わせ先がフォークであること。
- フォークで変えた部分の著作権者。
- Royalty-free 2.0 と Software 3.0 を、派生物の利用者にそのまま適用できるか。これは上流のライセンス文を読んで確かめる必要があります【推測】。
- crates.io に公開する場合は、名前に「Slint」を含めてよいか (商標) も確かめる必要があります。

### 比べると

| | git の依存 | patch の手順だけ | 別名で crates.io |
|---|---|---|---|
| アプリの `Cargo.toml` の変更 | `slint` の行を書き換え | `[patch.crates-io]` を足す | `slint` の行を書き換え |
| 上流に戻す手間 | 1 行戻す | patch を消す | 1 行戻す |
| リポジトリの公開 | 要る | 要る | 要らない |
| フォーク向けのライブラリを公開 | できない | 利用者ごとに patch が要る | できる |
| フォーク側の作業 | README だけ | README だけ | 改名、メタデータ、公開の手順 |
| 間違えたときの壊れ方 | ビルドが失敗する | 気づかずに上流でビルドすることがある | ビルドが失敗する |

推奨 1〜7 の目的 (評価する人に試してもらう) には、git の依存か patch の手順で足ります。
上流と比べてもらうなら patch、フォークだけを使ってもらうなら git の依存が分かりやすいです。
README には両方を書けます。crates.io への公開は、ライブラリを作る人が出てきてからでも間に合います。
