# 作業の順番

今の作業の順番と条件を置く、ただ 1 つの一覧です。相手は、当面オーナー自身です。
節目ごとにファイルを増やさず、この文書を書き換えます。終わった項目は消し、経緯はコミットに、決まりは `docs/design/` に書きます。1 万字を超えたら削ります。
確かめたものに【確認】、確かめていないものに【推測】と付けます。これまでの記録は `docs/plan.md` (Phase 0〜7) と `docs/recommendations-after-phase7.md` (2026-11-18〜20) にあります。

## 主張と費用

- 上流の `.slint` と Rust のコードが、手を入れずに動く。上流のテストケース、gallery、プローブ、上流の Rust の example と demo (23 個が起動して描け、残りは外した API か上流自身の不備)、実際のアプリ 1 つ (slokk-slint。`Cargo.toml` の 2 行で動き、画面はレイアウトが同じ) で確かめた【確認、`docs/design/upstream-examples.md`、`docs/design/app-compat.md`】。
- 上流の winit にまだない Windows の統合 (窓の外に出るポップアップ、ダークなメニュー、ドロップの受け側、タイトルバーへの統合)【確認、`docs/design/windows.md`】。どれも上流の winit への変更でも実現でき、言えるのは「今使える」まで。
- フォークでなければならない理由は、UI が Composition のビジュアルツリーであること。表示については実証した (2026-11-20、4): アプリの D3D11 のスワップチェーンと WebView2 を `Image` に置け、Slint の要素を上に重ねられ、クリップ、不透明度、スクロールが効き、内容が変わっても同期パスは走らない【確認、`docs/design/embedding.md`】。上流は毎フレーム画像を作り直して描き (`examples/ffmpeg`、`servo`)、WebView2 は子ウィンドウにしかできない【確認】。WebView2 への入力の転送も、上流の API と HWND だけでアプリが組めた (2026-11-21、6): クリック、ホイール、カーソル、IME、Tab、Alt+Tab、ポップアップの位置と閉じ方。できないのはアクセシビリティ (L)、ドロップ、ペンの筆圧【確認、`docs/design/embedding.md`】。wgpu 連携を外したフォークは、wgpu で描くアプリには後ろにいる。
- 費用: 速くも軽くもない (`docs/design/costs.md`)。実際のアプリでは gallery より重く、窓が上流より 60 ms 遅れて出て、private メモリは 128 MB、毎フレーム `Path` を作り直すアニメーションの CPU は上流の 2.3 倍【確認、`docs/design/app-compat.md`】。Rust だけ、Windows 11 22H2 以降、`=1.19.0` に固定、保守する人は 1 人。

## その後 (5 の判断しだい)

- 差し込みの API 化 (M): `slint::wuc` で、コンポジターと Visual を生の COM ポインターでやり取りする。倍率の変化をアプリに知らせる方法が要る。入力の転送はアプリの側に置き、例として `probe-embed` の転送 (`tests/probe/src/embed/web.rs`) を示す。
- 差し込んだ WebView2 のアクセシビリティ (L): ページの UI Automation のツリーを項目の下につなぐ。`accesskit_windows` に手を入れるか、フォーク自身のプロバイダーが要る。ドロップの転送 (M) はフォークのドロップの受け側に口を足す。
- TSF (L): オーナーの計画。slokk-slint で試せる。
- 1.20 への追従 (M〜L): 出たら試す。core の 58 ファイルを変え、約 12,500 行を足している【確認】。
- 外に広げる場合だけ: README の絵、窓の外に出られるポップアップの一行、Skia の数字、SixtyFPS への問い合わせ、`reuse lint`、NVDA。タグを動かす運用もやめる。

## やらないもの

| 項目 | 理由 | 見直す条件 |
|---|---|---|
| 倍率の違うモニターの間の移動 (slokk-slint と `probe-embed`) | 別の機械を用意する手間に見合わない (2026-11-21)。同じ機械の 125 % と `SLINT_SCALE_FACTOR=2` では配置が合う【確認】 | 別のモニターの環境を使うとき |
| ドラッグの送り側 (`start_drag`)、画像 (`CF_DIB`)、`CFSTR_PERFORMEDDROPEFFECT` | 上流の winit にもない。slokk-slint は `DragArea` も `DropArea` も使わない【確認】 | アプリが要るとき |
| スライドとリサイズの残りの引っかかり (M) | 1 コマ 12〜15 ms のうち 5〜7 ms が、UI Automation のクライアントがいるときのアクセシビリティの更新 (612 ノード)。上流が同じだけ払っているかは測れていない。100 ms への間引きはかえって悪かった【確認、`docs/design/app-compat.md`】 | 相手を広げるとき、またはオーナーのアプリで目立つ場面が増えたとき。先に上流の 1 コマを測る方法を作る |
| アニメーションの Composition への委譲 (L) | slokk-slint の引っかかるスライドは幅のアニメーションで、レイアウトと行の組み直しが要るので、委譲しても縮まない【推測】 | レイアウトに効かないアニメーション (位置、不透明度) で、フォークが上流より引っかかったとき。比べ方は `docs/design/costs.md` の Why Not |
| Mica と全機能のネイティブのメニューバーの併用 (L)、`SLINT_NO_MUDA` の API 化 | HMENU は必須でない (2026-11-19)。slokk-slint に `MenuBar` がない【確認】 | Alt/F10 と UI Automation の役割が要るアプリが出たとき |
| 設定への追従 (テキストのサイズ、アニメーションのオフ、ハイコントラスト) | 上流もしていない。スタイルは上流のコンパイラーの側にある | 相手に企業を含めるとき |
| Slint 描画のポップアップへの Acrylic | Fluent の背景が不透明で、効く場面が少ない | スパイクの副産物で安く出たとき |
| 言語バインディング、crates.io への別名公開 | L が続き、利用者がいない。商標の扱いを確かめていない | 外の利用者が求めたとき |
| 16384 px を超えるテキスト、コミット前に壊したテキストのアトラス、カスタムカーソル | 今のアプリで起きない | エディター型のアプリを作るとき |

## 確かめていないこと

- slokk-slint でフォークが重い理由: private メモリ 128 MB (gallery は 47 MB)、起動の 60 ms の遅れ、スプラッシュの CPU。判断に要るときに内訳を測る。

- 1.20 が crates.io に出たあとも、`slint = "1.19"` に対して patch の 1.19.0 が選ばれるか。
- 仮想化しない長いリストで毎フレームテキストが変わるときに、アトラスのページが残るか (`docs/design/visual-tree.md`)。
- `no-frame` の窓で、`WS_CAPTION` がないことによる、スナップや最小化のアニメーションの違い。
- ポップアップのフォーカスを NVDA が読むか。
- 追わないもの (判断を左右しない): JAWS、`no-frame` と MenuBar の併用、`DwmEnableBlurBehindWindow` が透けなかった理由、管理者権限のアプリへのドロップ。
